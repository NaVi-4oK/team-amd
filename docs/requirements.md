# Сценарии работы программы

## Общие положения

Участник — исследователь геомагнитных данных.

Программа работает локально на компьютере исследователя.
Источником внешних данных является INTERMAGNET HAPI.

Импорт, обработка и чтение данных являются отдельными
операциями. Импорт и обработка создают отдельные Job.
Чтение сохранённых данных не создаёт Job.

Связь компонентов:

CLI → Dispatcher → Registry → Tool → ToolResult.

Job контролирует собственные допустимые переходы.
Dispatcher управляет выполнением операций, а Registry
выдаёт Tool по имени операции.

В практике 3 реализуется доменное ядро без HTTP-сервера
и базы данных. Постоянное хранение и пользовательский
интерфейс относятся к дальнейшей разработке.

## Общие правила

- Сохранять исходный ответ источника и метаданные.
- Сохранять подтверждённые сведения об обсерватории,
  компоненте, единицах, cadence и publication state.
- Не подменять пропуски нулевыми измерениями.
- Не исправлять измерения автоматически.
- Не угадывать отсутствующие обязательные метаданные.
- Не изменять сырой набор при обработке.
- Не публиковать незавершённый результат.
- Возвращать ошибки с кодом, сообщением и деталями,
  если они необходимы.
- Не раскрывать секреты и необработанные внутренние
  исключения в пользовательских сообщениях.

Полноценная проверка научного качества измерений
относится к дальнейшему развитию проекта.

## Сценарий 1. Получить сырые измерения

**Участник:** исследователь.

**Цель:** получить геомагнитные измерения выбранной
обсерватории за указанный период.

### Основной порядок

1. Исследователь задаёт обсерваторию, publication state,
   cadence, компоненты, период и ключ идемпотентности.
2. Программа проверяет запрос.
3. Dispatcher создаёт Job импорта в состоянии Created.
4. Job переходит в Downloading.
5. Import Tool получает данные через адаптер INTERMAGNET.
6. Программа проверяет ответ и сохраняет сырой набор.
7. Job переходит в Completed.

### Критерии приёмки

- Корректный запрос создаёт Job импорта.
- Успешный импорт сохраняет исходные данные
  и метаданные происхождения.
- HAPI status 1201 создаёт пустой сырой набор
  и считается успешным импортом.
- Некорректные параметры отклоняются до создания Job.
- Повтор с тем же ключом и параметрами возвращает
  прежний Job без повторного обращения к источнику.
- Повтор с тем же ключом и другими параметрами
  возвращает idempotency_conflict.

## Сценарий 2. Обработать сырой набор

**Участник:** исследователь.

**Цель:** получить отдельный результат обработки
ранее сохранённых измерений.

### Основной порядок

1. Исследователь выбирает сырой набор.
2. Указывает метод обработки, его параметры
   и ключ идемпотентности.
3. Программа проверяет существование набора
   и допустимость метода.
4. Dispatcher создаёт отдельный Job обработки.
5. Job переходит из Created в Processing.
6. Processing Tool выполняет выбранный метод.
7. Результат сохраняется как отдельный набор.
8. Job переходит в Completed.

### Критерии приёмки

- Обработка создаёт новый обработанный набор.
- Обработанный набор содержит ссылку на исходный.
- Сырой набор не изменяется.
- Неизвестный метод отклоняется до создания Job.
- Отсутствующий сырой набор отклоняется до создания Job.
- Ошибка во время вычисления переводит Job в Failed.
- Повтор с тем же ключом не запускает обработку заново.
- Новый ключ позволяет создать новый результат.

В практике 3 реализован демонстрационный метод
`count_records`. Научные методы будут определяться
и добавляться отдельно.

## Сценарий 3. Получить сохранённые данные

**Участник:** исследователь.

**Цель:** прочитать сырой или обработанный набор.

### Основной порядок

1. Исследователь указывает тип набора.
2. При необходимости задаёт идентификатор или фильтры.
3. Query Tool читает сохранённые наборы.
4. Программа возвращает конкретный набор либо страницу
   кратких описаний.

### Критерии приёмки

- Чтение не создаёт Job.
- Внешний источник при чтении не вызывается.
- Неизвестный идентификатор даёт dataset_not_found.
- Неверные фильтры дают invalid_query.
- Незавершённые и ошибочные наборы недоступны для чтения.
- Порядок страниц остаётся стабильным при появлении
  новых наборов между запросами.

## Сценарий 4. Источник отклонил запрос

**Участник:** исследователь.

**Цель:** получить понятную причину ошибки импорта.

### Основной порядок

1. INTERMAGNET возвращает ошибку запроса или набора.
2. Import Tool сопоставляет HAPI status с доменной ошибкой.
3. Dispatcher переводит Job в Failed.
4. Сырой набор не публикуется как готовый.

### Критерии приёмки

- Ошибка неизвестного набора отображается
  как dataset_unavailable.
- Остальные ошибки HAPI 14xx отображаются
  как intermagnet_request_rejected.
- Такие ошибки не вызывают повторный запрос.
- Пользователь получает безопасное описание причины.

## Сценарий 5. Источник недоступен или прислал неверные данные

**Участник:** исследователь.

**Цель:** получить понятную ошибку вместо зависания
или повреждённого результата.

### Основной порядок

1. Адаптер сообщает о сетевой ошибке или ошибке сервера.
2. Import Tool выполняет ограниченное число попыток.
3. Если получить данные не удалось, Job становится Failed.
4. Полученный ответ проверяется перед сохранением.
5. Некорректный ответ не публикуется как готовый набор.

### Критерии приёмки

- Сетевые ошибки обрабатываются без бесконечных повторов.
- После исчерпания попыток возвращается
  intermagnet_unavailable.
- Некорректное тело HAPI-ответа приводит к
  intermagnet_invalid_response.
- Ошибка сохранения не позволяет опубликовать набор.

В практике 3 предусмотрено не более двух попыток
получения данных. Ошибки источника проверяются
через тестовый адаптер.

Настоящие сетевые тайм-ауты, задержки повторов,
ограничения размера ответа и полная проверка
метаданных относятся к реализации HTTP-адаптера.

## Сценарий 6. Отклонить неверный запрос

**Участник:** исследователь.

**Цель:** исправить параметры и повторить операцию.

### Основной порядок

1. Пользователь передаёт неизвестную операцию
   или некорректные параметры.
2. Registry либо вызывающая сторона отклоняет запрос.
3. Возвращается код ошибки и указание проблемного поля,
   если ошибка связана с параметрами.
4. Пользователь исправляет запрос.

### Критерии приёмки

- Неизвестная операция даёт unknown_operation.
- Неверный период импорта даёт invalid_import_request.
- Неверные параметры обработки дают
  invalid_processing_request.
- Некорректные фильтры чтения дают invalid_query.
- Ошибка валидации нового запроса не создаёт Job.

## Сценарий 7. Восстановление прерванных заданий

**Участник:** исследователь.

**Цель:** получить конечное состояние задания,
которое не завершилось до остановки приложения.

### Основной порядок

1. При запуске приложения проверяется история Job.
2. Незавершённые Job в Created, Downloading
   или Processing переводятся в Failed.
3. Сохраняется ошибка job_interrupted.
4. Повтор с прежним ключом возвращает прежний Job.
5. Новый запуск требует нового ключа.

В практике 3 этот сценарий проверяется в памяти.
Настоящее восстановление после перезапуска требует
постоянного хранилища.

## Состояния Job и разрешённые переходы

### Импорт

- Created → Downloading.
- Created → Failed.
- Downloading → Completed.
- Downloading → Failed.

### Обработка

- Created → Processing.
- Created → Failed.
- Processing → Completed.
- Processing → Failed.

Completed и Failed — конечные состояния.
Другие переходы отклоняются явной ошибкой
invalid_job_transition без изменения состояния.

Переход Downloading → Processing запрещён:
импорт и обработка являются отдельными Job.

Отмена, удаление и повторный запуск существующего Job
не предусмотрены.

## Согласованность результата

Tool сохраняет набор до успешного завершения Job.

Хранилище публикует набор только при условии, что
связанный Job имеет состояние Completed и содержит
идентификатор этого набора.

В практике 3 согласованность видимости обеспечивается
хранилищем в памяти. Постоянное атомарное сохранение
результата и Job будет обеспечиваться средствами БД.

## Что предложил ИИ на практике 1

### Исходный промпт

«Мы делаем агрегатор геофизических данных.
Первая версия собирает геомагнитные измерения
по источнику, станции и периоду.
Найди ещё 3 способа сломать основной сценарий:
получение данных, проверка и сохранение результата.
Объясни последствие и предложи проверяемую защиту».

### Предложения и решения

1. Повтор запроса после потери связи может запустить
   сбор дважды. Принято: использовать ключи
   идемпотентности. Реализовано в практике 3.

2. При обработке могут потеряться единицы измерения,
   сведения об обсерватории и происхождении.
   Принято: сохранять подтверждённые метаданные
   и связь обработанного результата с исходным набором.
   Базовое хранение происхождения реализовано в П3.
   Полная научная проверка метаданных ещё не реализована.

3. Источник может прислать данные только за часть
   запрошенного периода. Принято как направление
   дальнейшего развития: проверять покрытие и пропуски.
   Полноценный отчёт о покрытии в П3 не реализован.

После практики 2 архитектура уточнена:
используется один внешний источник INTERMAGNET,
а импорт, обработка и чтение разделены на три Tool.
