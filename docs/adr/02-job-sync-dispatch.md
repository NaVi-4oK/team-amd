# ADR-0002: Разделить импорт, обработку и чтение данных

- Дата: 2026-11-22
- Статус: предложено

## Контекст

Пользователь описал три отдельные операции локальной программы: загрузить сырые геомагнитные данные из разных обсерваторий через один API, обработать выбранный сырой набор и прочитать сохранённые данные. Это разные действия с разными источниками ошибок и правами на изменение данных.

## Решение

Реализовать три независимых контракта Tool:

1. `ObservatoryApiTool` обращается к единому внешнему API и возвращает сырой набор без научного исправления значений.
2. `GeomagneticProcessingTool` получает выбранный сырой набор и параметры метода, возвращает отдельный обработанный набор.
3. `LocalDataQueryTool` читает сырые и обработанные наборы из локальной базы и не обращается к сети.

Локальный сервис оркестрирует эти Tool и единолично управляет сохранением. Поэтому ошибки обработки не изменяют исходные сырые записи, а чтение не запускает повторную загрузку.

Для импорта и обработки создаются отдельные Job. Они выполняются внутри локального приложения; отдельная облачная очередь или брокер в описанную модель не входят. Чтение выполняется синхронно без Job. Идемпотентность повторных команд импорта/обработки сохраняется по `Idempotency-Key`.

## Модель состояний

- Импорт: `Created → Downloading → Completed | Failed`; если запуск не состоялся — `Created → Failed`.
- Обработка: `Created → Processing → Completed | Failed`; если запуск не состоялся — `Created → Failed`.
- Любой иной переход запрещён. Повторная обработка создаёт новый Job и новый набор, связанный с исходным.

## Альтернативы

- Один универсальный Tool для всех операций: смешивает сетевые запросы, вычисления и чтение/запись базы, усложняет проверку ошибок и границ данных.
- Обрабатывать данные сразу при скачивании: не позволяет отдельно повторно выбрать метод обработки для уже сохранённых сырых данных.
- Использовать внешний API также для чтения ранее полученных данных: противоречит локальному хранению и делает чтение зависимым от сети.

## Последствия

- Каждый Tool можно проверить отдельно по своему входу, результату и ошибкам.
- Исходный набор сохраняется и может использоваться для нескольких независимых запусков обработки.
- Нужна транзакционная граница, связывающая запись результата и завершение соответствующего Job.
- Формат сырых записей зависит от ещё не выбранного API; формат обработанного результата зависит от методов, которые команда согласует отдельно.
- Прерывание приложения во время задания и возобновление после запуска не определены этим ADR и требуют отдельного решения, если это войдёт в требования.

## Пересмотр

Если команда выберет единый конвейер «скачать и сразу обработать», появится отдельная очередь заданий или потребуется восстановление незавершённых заданий после перезапуска.
