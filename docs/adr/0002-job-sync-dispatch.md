# ADR 0002: Фоновые Job с локальной историей и идемпотентностью

## Контекст и ограничения

Импорт и обработка временных рядов могут выполняться
дольше интерактивной команды CLI.

Исследователю необходимо получить Job ID,
проверить состояние задания и избежать повторного
выполнения при повторной отправке команды.

Job выполняются внутри одного локального процесса.
Распределённая очередь и удалённые worker не вводятся.

Отмена и автоматическое возобновление прерванных
заданий не поддерживаются.

## Решение

Импорт и обработка выполняются отдельными Job.

Целевая программа выполняет их в фоновом режиме.
CLI возвращает Job ID, а команда job-status позволяет
проверить состояние задания.

Dispatcher не зависит от конкретных Tool.
Для определения инструмента используется Registry.

Повтор с тем же ключом, операцией и параметрами
возвращает существующий Job.

Тот же ключ с изменёнными параметрами или операцией
отклоняется с idempotency_conflict.

Ключи идемпотентности являются общими
для операций импорта и обработки.

Проверка существующего запроса выполняется
до повторной валидации Tool.

Проверка и создание нового Job выполняются атомарно.

## Жизненный цикл

Импорт:

```text
Created → Downloading → Completed
                      → Failed
Created → Failed
```

Обработка:

```text
Created → Processing → Completed
                     → Failed
Created → Failed
```

Completed и Failed являются конечными состояниями.

Все остальные переходы запрещены и отклоняются
самим Job с ошибкой invalid_job_transition.

Completed фиксируется только после сохранения
соответствующего набора.

Частично сохранённый результат не публикуется
как готовый.

## Восстановление прерванных заданий

При запуске приложения Job, оставшиеся в состояниях
Created, Downloading или Processing, переводятся
в Failed с ошибкой job_interrupted.

Проверка выполняется до запуска новых заданий.

Состояние Created также включено в восстановление:
приложение может завершиться после создания Job,
но до фактического запуска Tool.

Автоматический повтор не выполняется.

Повтор с прежним ключом идемпотентности возвращает
этот же Job. Для новой попытки необходим новый ключ.

## Последствия

- История Job и ключи идемпотентности должны
  сохраняться между перезапусками целевой программы.
- Для постоянного хранилища необходимы атомарная
  проверка ключей и создание Job.
- Состояние Completed и результат должны
  сохраняться согласованно.
- Чтение сохранённых наборов остаётся синхронной
  операцией без создания Job.
- Отмена и повторный запуск существующего Job
  не поддерживаются.

## Рассмотренные варианты

### Только синхронное выполнение

CLI остаётся заблокированным на время получения
или обработки данных.

В качестве основной архитектуры не выбран.
Синхронный режим допускается для тестирования ядра.

### Не хранить историю Job

Теряются состояния заданий и возможность определить,
был ли запрос уже выполнен.

Вариант отклонён.

### Создавать Job на каждый повтор запроса

Может привести к повторному импорту или обработке.

Вариант отклонён в пользу идемпотентности.

### Поддерживать отмену Job

Безопасное прекращение внешнего запроса и очистка
частичного результата пока не определены.

Отмена не включена в текущий контракт.

## Уточнения по реализации практики 3

Dispatcher поддерживает синхронное выполнение
и выполнение через переданный executor.

Репозитории реализованы в оперативной памяти.
Сохранение истории после фактического перезапуска
пока отсутствует.

Восстановление незавершённых Job проверяется
путём имитации прерывания с сохранённым
в памяти объектом Job.

По результатам аудита добавлены проверки:

- конфликт ключа до повторной валидации Tool;
- возврат существующего Job без повторной валидации;
- отклонение некорректных JSON-параметров;
- восстановление Job, оставшегося в Created.

Постоянное хранение и настоящая процедура запуска
приложения относятся к дальнейшим практикам.
